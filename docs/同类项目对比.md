# 同类开源项目对比

2026-11-09 查的。做法：先在网上搜 GitHub 上「让多个编程 agent 在一起协作」的开源项目，再读各家 README。**没有安装、没有运行过其中任何一个**，下面写的都是它们自己 README 里说的，没写的地方写「没写」。星数是当时页面上的数，会变。

## 一、最像的：让 agent 聚在一间房里

| 项目 | 星数 | 许可 | 一句话 | 在线 agent 怎么收到消息，离线的怎么办 |
|---|---|---|---|---|
| [agentchattr](https://github.com/bcurts/agentchattr) | 1.6k | MIT | 本地网页聊天室，agent 互相 @；支持 Claude、Codex、Gemini、Copilot、Kimi、Qwen、Kilo、CodeBuddy、MiniMax | 靠每个 agent 的包装程序送达，agent 离线时消息排队，等包装程序下次来取 |
| [agmsg](https://github.com/fujibee/agmsg) | 1.6k | MIT | 用本地 SQLite 做的跨厂商消息层，纯命令行，不要常驻进程 | 要有运行中的会话；能用 `spawn` 在 tmux 里开新 agent |
| [hcom](https://github.com/aannoo/hcom) | 650 | MIT | agent 互相发消息、监视、拉起对方；终端里一个仪表盘；能跨机器（MQTT 中继）；支持 Windows | 钩子只对用 `hcom` 启动的 agent 有效；空闲的会被立刻唤起；完全关掉的是否能唤起，没写 |
| [Agent Chat](https://github.com/Alex-R-A/multi-agent-collaboration-mcp) | 1 | Apache-2.0 | 本地共享聊天室，一个项目一个房间 | 它自己写「不启动任何 agent」，agent 要自己在跑并轮询 |
| [agent-room](https://github.com/robinAKL/agent-room) | 106 | MIT | 实时房间，带「决定 / 待办 / 状态」标记，和一个任务板（要另一个 agent 验证才算完成）；可自己托管，默认用它的托管服务，房间 24 小时过期 | 只有注册过的常驻助手能被网络请求唤起，别的要自己在跑 |
| [mcp_agent_mail](https://github.com/Dicklesworthstone/mcp_agent_mail) | 约 1.9k（第三方列表） | 没核对 | agent 之间的邮箱，加文件预约（防止互相覆盖） | 没读 README，只看了搜索摘要 |

## 二、另一类：管理一堆 agent 的工具（agent 之间不说话）

| 项目 | 星数 | 许可 | 一句话 |
|---|---|---|---|
| [vibe-kanban](https://github.com/BloopAI/vibe-kanban) | 28.6k | Apache-2.0 | 看板，每个任务一个分支一个工作区；**README 第一行写着「Vibe Kanban is sunsetting」**，要停更了 |
| [claude-squad](https://github.com/smtg-ai/claude-squad) | 8.8k | AGPL-3.0 | 终端界面，每个任务一个 git worktree 和 tmux 会话 |
| [agent-deck](https://github.com/asheshgoplani/agent-deck) | 1.2k | MIT | 终端界面（也有网页）；能看 Claude 的 5 小时和 7 天额度；Windows 只支持 WSL。这一条有一部分来自页面摘要，不是原文 |

## 三、并坐现在的位置

下面「并坐」一栏是这个仓库里实际有的，大部分在开发过程中真跑过，没跑过的写了。

| 方面 | 并坐 | 别人（只看我读到的 README） |
|---|---|---|
| 唤起离线的 agent | **点名就叫醒**：房间自己运行对应客户端的续接命令。真叫醒过 Claude、Codex、Cursor、CodeBuddy、WorkBuddy、Antigravity、DeepSeek | 基本要 agent 已经在跑，或要从它们的启动器进去 |
| 界面 | 中文网页指挥台；一个项目一间房；左边项目栏 | agentchattr 英文网页；hcom、claude-squad、agent-deck 以终端为主 |
| 待办与验收 | 待办带步骤；agent 请验收，**只有用户能点通过或打回**，打回要写理由；已完成的不能再改，只能复制一份 | agentchattr 有 Jobs；agent-room 有「换人验证」的任务板；其余没写 |
| 权限 | 唤起的 Claude 要的权限变成卡片；agent 可申请这一次的完整权限 | 多数只有「自动全批准」的启动参数 |
| 向用户提问 | 提问卡片（单选、多选、自己写） | agentchattr 有决定卡片 |
| 房间自己开新会话 | 能：Claude、DeepSeek、Codex、Cursor、Antigravity、CodeBuddy、WorkBuddy；可选模型、思考强度、目录（项目目录、新 worktree、临时目录、自己填） | hcom、agmsg 能开；agentchattr 靠用户运行启动器 |
| 账号额度 | Claude、Codex、Antigravity、Cursor 的 5 小时 / 每周 / 每月；撞到额度弹卡片，重置后自动继续；还有插件递交用量的接口 | 只有 agent-deck 有，且是 Claude 和 Z.ai |
| 速度 | 内置 token 速度看板，席位栏每家一行 | 没看到 |
| 多项目 | 一个项目一个房间，项目栏切换 | agentchattr 要每个项目开一个实例；Agent Chat、agent-room 有多房间 |

## 四、并坐的短板

- **看不到 agent 正在跑的终端。** 每次叫醒是起一个无界面的进程跑完一轮。hcom、claude-squad、agent-deck 能看到实时终端、能直接接管。
- **只能在这一台电脑上。** hcom 能跨机器。
- **Windows 没有实机测过**（代码做了适配）。hcom、agentchattr、agmsg 都写了支持 Windows。
- **一半客户端没测过。** 19 家里本机装了的只有 8 家左右，其余是照文档写的。
- **只有一个用户**，权限和安全按「这台电脑上的你」设计。
- **没有「代码评审、辩论」这类现成的多 agent 流程**（agentchattr 有模板）。
- 仓库自己的星数和更新日期，这次没查。

## 五、没核对的

- 各家最近一次提交的日期，页面上都没读到。
- hcom 对完全关掉的 agent 能不能唤起，README 没写。
- mcp_agent_mail 只看了搜索摘要，没读 README。
- agent-deck、agmsg 的页面被截断，标了「摘要」的地方不是原文。
- 对方的功能都没有实际运行验证。

## 六、方向（只是建议，没定）

别人要么做聊天室，要么做管理器，没有看到哪个把「人在中间指挥」做完整：离线唤起、验收、权限、额度这几块是并坐已经拉开差距的地方，值得继续做深。「看实时终端」是别人最强、也和并坐现在的做法冲突最大的一块，先想清楚要不要补，再动手。
