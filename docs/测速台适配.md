# Token 测速台：各家怎么接进来

给要改测速台、或要给它加一家客户端的 agent 看。用户看到的说明在 `MAINTENANCE.md` 的「Token 测速台（内置）」一节，这里只讲适配：数据从哪来、怎么算、加一家要动哪几处。

测速台只读本机各家客户端自己写的会话记录，不联网、不调接口、不改原始文件。所以「适配一家」的意思是：找到它把每次回复的时间和 token 记在哪里，写一个解析器，把记录变成统一的一行。

## 数据怎么流

```
页面
  席位栏速度行 components/room/speed-line.tsx  ── GET /api/v1/speed
  测速台大弹窗 components/room/speed-board.tsx ── GET /api/v1/speed/board?range=…&v=…
        │
lib/speed.ts（在 Next 服务进程里）
  按需起一个 Node 子进程，用 IPC 发 {op: "summary" | "query"}
  摘要结果缓存 10 秒；子进程 5 分钟没人问就退出
        │
scripts/speed-worker.mjs（独立子进程）
  discover() 找文件 → updateOne() 按文件类型解析 → 每次回复变成一行
  增量结果存 data/speed-cache.json
  summary() 给速度行，query() 给看板
```

扫描放在子进程里，是因为会话记录加起来有几个 GB。在 Next 进程里读会卡住房间，也会撑大它的内存（自测时子进程峰值约 860 MB）。

什么时候重扫：上次扫描超过 15 秒（摘要）或 2.5 秒（看板）就重扫；带 `?fresh=1` 会强制重扫。重扫靠缓存只读新增部分，通常几十毫秒。

## 统一的一行

每次回复（一次模型请求）在 worker 里存成一个数组：

| 下标 | 字段 | 说明 |
|---|---|---|
| 0 | agent | 哪家：0 claude、1 codex、2 antigravity、3 dsh（`AGENT_INDEX`） |
| 1 | start | 请求开始的时间，秒；不知道就是 `null` |
| 2 | end | 回复结束的时间，秒 |
| 3 | out | 输出 token |
| 4 | model | 模型名（看板接口里换成 `models` 数组的下标） |
| 5 | project | 工作目录的最后一级（看板接口里换成 `projects` 的下标） |
| 6 | reasoning | 思考 token，没有记 0 |
| 7 | ttft | 等到第一个 token 或第一块的秒数，不知道就是 `null` |
| 8 | inp | 输入 token，**包含**缓存读和缓存写 |
| 9 | cread | 缓存读 |
| 10 | cwrite | 缓存写 |
| 11 | dedupId | 可选。同一次回复可能出现在两个文件里，比如桌面端和被房间叫醒的会话各存一份；有它就按它去重 |

前端的类型定义在 `lib/speed.ts` 的 `SpeedBoardRow`，只有前 11 个字段。

速度怎么算：**`out / (end - start)`**，分母从请求发出算到回复结束，包含等第一个 token 的时间。所以它是「这次回复从发出到写完的平均速度」，不是纯解码速度。`start` 是 `null` 或 `end <= start` 的行不参与算速度，但照样算进 token 用量。

## 现在的四家

### Claude Code（`claude`）

- **文件**：`~/.claude/projects/**/*.jsonl`，纯文本，按字节偏移增量读。
- **预筛**：一行里没有 `"type":"assistant"` 或 `"type":"api-request"` 就不 `JSON.parse`。
- **开始**：`api-request` 那一行的 `timestamp`。
- **回复**：`assistant` 行，按 `message.id` 归并。一次回复会拆成好几行（每个内容块一行），所以：
  - `end` 取这些行里最晚的时间；
  - `out` 取最大的 `usage.output_tokens`；
  - 输入、缓存读、缓存写取最后一行的。
- **跳过**：`model` 是 `<synthetic>` 的行（客户端自己造的，不是模型回复）。
- **思考**：`usage.output_tokens_details.thinking_tokens`。
- **首块**：第一条 `assistant` 行的时间减去请求开始。日志只在一整块内容写完后才落盘，所以这是上限，页面上显示成「首块 ≤」（`firstChunk: true`）。

### Codex（`codex`）

- **文件**：`~/.codex/sessions/` 和 `~/.codex/archived_sessions/` 下的 `*.jsonl`，以及压缩的 `*.jsonl.zst`。同名的纯文本文件已经在的话，跳过 `.zst`。
- **预筛**：只看每行前 260 字节里的 `"type":"…"`，需要时才解析整行。
- **开始**：下面任一事件都会把开始时间设成它的时间：
  - 工具结果回去了（`response_item` 里的 `…_call_output`）；
  - 用户消息完成（`item_completed` + `UserMessage`）；
  - `task_started`；
  - `compacted`。

  记完一行之后，开始时间设成这行的结束时间（下一次请求接着发）。
- **回复**：`token_usage_record` 事件的 `payload.usage`（`output_tokens`、`reasoning_output_tokens`、`input_tokens`、`cached_input_tokens`、`cache_write_input_tokens`）。
- **模型和目录**：`turn_context` 里的 `model`、`cwd`；`session_meta` 也给 `cwd`。
- **首 token**：`task_complete` 里的 `time_to_first_token_ms`，填给这一轮的第一行。这是客户端自己量的准数（`firstChunk: false`）。
- 注意：这一列是「Codex 这个客户端」，不是 OpenAI。Codex 接了 DeepSeek 等别家模型时，也记在这一列，模型名照实显示。

### Antigravity（`antigravity`）

- **文件**：`~/.gemini/antigravity/conversations/*.db` 和 `~/.gemini/antigravity-cli/conversations/*.db`，SQLite，用 Node 24 自带的 `node:sqlite` 只读打开，字段是 protobuf，用 worker 里的小解码器 `pbFields` 读。
- **变化判断**：签名里带上 `-wal` 文件的修改时间和大小，因为没提交进主库的写入还在 WAL 里。有变化就整库重读。
- **回复**：`steps` 表里 `step_type = 15` 的行，`metadata` 字段：
  - 1 开始时间，6 第一块时间，7 结束时间；
  - 9 用量：3 输出、2 输入、5 缓存读、9 思考、11 回复 id。
- **模型**：`gen_metadata` 表，按回复 id 对上（1 → 19 是模型名，1 → 4 → 11 是回复 id）。对不上就用最近一个模型名。
- **项目**：`conversation_summaries.db` 的 `workspace_uris` 第一项。
- **去重**：`agy:<回复 id>`。
- **首块**：上限（`firstChunk: true`）。
- 这些字段号是对着本机数据认出来的，没有官方文档。客户端升级后速度行要是消失了，先查这里。

### DeepSeek Harness（`dsh`）

- **文件**：`~/.dsh/sessions/**/session.v4.jsonl.zstd`。每条事件追加成一个独立的 zstd 帧，而 Node 的 `zlib.zstdDecompressSync` 只解第一帧，所以用 `eachZstdFrame` 按帧魔数逐帧解。有变化就整个文件重读。
- **事件**：
  - `session`：给 `cwd`；
  - `step/start`：开始时间，毫秒；
  - `assistant/message`：一次回复。
- **回复字段**：
  - `data.usage`：`outputTokens`、`inputTokens`、`cacheReadTokens`、`cacheWriteTokens`；
  - `data.stream[0].time`：第一块到达的时间，减去开始时间就是首 token；
  - `data.message.source.replayState.response.responseModel`：模型名，没有就用 `source.model`。
- **去重**：`dsh:<message.id>`。

### Windows 那份

`homes()` 除了本机主目录，还会看 `WIN_USERS`（写死的 `/media/AverageJoe/系统1/Users`，这台电脑双系统挂上来的 Windows 分区）。下面哪个用户目录里有这四家的文件夹，就一起扫，项目名后面加「 · Win」。换一台电脑，这个路径不存在，就自动跳过。

## 摘要和看板怎么取

**席位栏摘要**（`summary()`）：每家只看近 24 小时、`out ≥ 100` 且知道开始时间的行，取最后 30 条。

- `tps`：最新一条的速度；
- `median`：这 30 条的中位数；
- `ttft`：24 小时里最近一条有首 token 的行；
- `firstChunk`：Claude 和 Antigravity 是 `true`。

页面按 `speed.kind === kind.id` 把它挂到花名册那一家下面，所以 worker 里每家的 key 必须和 `lib/kinds.ts` 里的 `id` 一模一样。

**看板**（`query()`）：

- 范围 `1h`、`24h`、`7d`、`30d`、`all`；
- 模型名、项目名去重成数组，行里只存下标；
- 版本号是「文件内容的哈希 + 范围 + 30 秒一档」，前端带着上次的 `v` 来问，没变就只回 `{unchanged: true}`。

## 缓存

`data/speed-cache.json`：`{ v: CACHE_VERSION, files: { 路径: { kind, tag, sig, offset, state, rows } } }`。

- 纯文本 jsonl 记字节偏移和解析器状态（`state`），下次从偏移接着读。末尾没读完的半行不算，偏移停在它前面。
- `.zst`、`.zstd`、`.db` 没法从中间接着读，签名（修改时间 + 大小）一变就整个重读。
- **改了解析规则、行格式或 `AGENT_INDEX`，一定要把 `CACHE_VERSION` 加一**。不加的话，旧文件的旧结果会一直留在缓存里，因为文件签名没变，不会重读。

## 能调的地方

测速台没有配置文件，也不读环境变量，不用装任何东西：只要本机有这几家的会话记录，打开房间就能用。下面这些数都写在代码里，要调就改常量。

**`scripts/speed-worker.mjs`**

| 常量 | 现在的值 | 管什么 |
|---|---|---|
| `MIN_SUMMARY_TOKENS` | 100 | 输出少于它的回复不算进席位栏速度（太短的回复速度不准） |
| `SUMMARY_LAST` | 30 | 席位栏中位数取最近几次 |
| `RANGES` | 1h / 24h / 7d / 30d / all | 看板的时间范围选项 |
| `WIN_USERS` | `/media/AverageJoe/系统1/Users` | 额外扫描的 Windows 分区用户目录；不存在就跳过 |
| `CACHE_VERSION` | 2 | 缓存格式版本，改了解析就加一 |
| `CHUNK_SIZE` | 512 KB | 读纯文本记录时每次读多少字节 |
| `handleRequest` 里的 `maxAge` | 摘要 15 秒，看板 2.5 秒 | 隔多久才重扫一次文件 |
| 摘要的时间窗 | 24 小时（`summary()` 里的 `86400`） | 席位栏只看这么久以内的回复 |

各家读哪些目录写在 `discover()` 里，路径都相对用户主目录，没有开关。

**`lib/speed.ts`**

| 常量 | 现在的值 | 管什么 |
|---|---|---|
| `IDLE_SHUTDOWN_MS` | 5 分钟 | 子进程没人问多久就退出，退出后内存还给系统 |
| `SUMMARY_KEEP` | 10 秒 | 摘要在 Next 进程里缓存多久 |
| `ask()` 的超时 | 45 秒 | 第一次全量扫描很慢时，超过这个时间就报「读取会话速度超时」 |

**页面**

- 速度行每 30 秒拉一次（`speed-line.tsx` 的 `EVERY`），3 分钟没动静数字变灰（`IDLE_AFTER`）。
- 看板上的选择（哪家、时间范围等）存在浏览器的 localStorage 里，键名是 `bench-speed:…`，每个浏览器各记各的，不进仓库。

**数据**

- `data/speed-cache.json`：扫描缓存，删掉也没事，下次会全量重扫一遍，第一次会慢一些。`data/` 在忽略名单里，不会被提交。

## 加一家要改哪几处

假设新客户端在 `lib/kinds.ts` 里的 id 是 `foo`。

**扫描（`scripts/speed-worker.mjs`）**

1. `AGENTS` 和 `AGENT_INDEX` **加在末尾**。下标存在缓存里，已有的不能挪。
2. 写解析器 `feedFooLine(lineBuf, rows, st)`（或者像 Antigravity 那样整文件读）。每次回复往 `rows` 推一行上面那 11 个字段，同一回复可能出现在两处的话加第 12 个字段去重。
   - 先按字节预筛（`Buffer.includes` 或只看行首几百字节），再 `JSON.parse`。会话记录很大，每行都解析会慢一个数量级。
   - 能拿到「请求开始」就填 `start`，拿不到填 `null`。不要拿上一条消息的时间凑，那样算出来的速度会虚低。
   - 首 token 是客户端自己量的就是准数；从日志落盘时间推的只是上限，要在第 5 步标出来。
3. `discover()` 里加上它的文件位置。不是纯文本 jsonl 的，在 `updateOne()` 里加一个整文件读的分支。
4. `summary()` 里 `byAgent` 写死了 4 个空数组，要加一个。`firstChunk` 的判断里，首 token 是上限的就加进去。
5. `homes()` 的存在性检查里加上它的目录，Windows 分区里的才会被扫到。
6. `CACHE_VERSION` 加一。

**页面**

7. `components/room/speed-board.tsx`：
   - `AgentKey` 类型；
   - `AGENTS` 列表（名字、品牌色、`exactTtft`、`ttftLabel`）；
   - `usePref("agent", …)` 允许的值；
   - 筛选下拉框的选项；
   - 页脚「读哪些目录」那句。
8. `lib/speed.ts` 里 `SpeedBoardRow` 那行注释的编号，以及 `app/speed/page.tsx` 的页面描述。
9. 席位栏速度行不用改，只要 key 和 `lib/kinds.ts` 的 id 一致就会自己出现。

**说明**

10. `MAINTENANCE.md` 的测速台一节和本文「现在的四家」各补一段。

## 怎么验

```bash
# 在临时目录里跑：自测会把缓存写到当前目录的 data/speed-cache.json，
# 在仓库里跑会覆盖房间正在用的缓存。
mkdir -p /tmp/speedtest && cd /tmp/speedtest
node /path/to/bench/scripts/speed-worker.mjs --bench-selftest
rm -rf /tmp/speedtest
```

自测会打出文件数、增量扫描耗时、内存，每家的摘要，以及 24 小时和全部的行数。新加的那家要出现在 `summary.speeds` 里，数字要和你在它自己界面上看到的大致对得上。

然后在房间里看：

- `curl -s 'http://127.0.0.1:4399/api/v1/speed?fresh=1'` 里有这一家；
- 花名册那一家下面出现速度行；
- 测速台里这家的卡片、筛选和明细都正常。

改了 worker 之后，正在跑的子进程还是旧代码。等它 5 分钟空闲退出，或者重启房间服务，才会用上新的。
