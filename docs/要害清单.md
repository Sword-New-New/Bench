## 1. 叫醒和队列

- **是什么**：
  监听群里每一条新消息（`onMessage(wake)`），找出被 `@` 的席位，按席位维护单飞队列（`Lane`）。同一个席位同一时刻只跑一个子进程（`queue.running`）；忙时又被 `@` 的消息排进 `queue.pending`，等当前这轮结束或中途由 `takeQueued` 领走后合批接着跑；agent 之间互 `@` 没有轮数上限（2026-11-11 用户定的；早先是满 3 轮刹住）：一条线在某个席位收尾（【本轮结束】 / `end: true`，不 @ 任何人）或用户插话时停，每个席位仍记着自己是第几跳；守着 `bench_wait` 的席位先走 `watchStandby` 宽限，若宽限期过了仍未取走则回退到命令唤起；进程输出达终态结果（`parser.ended()`）但未退出时 `END_GRACE_MS`（3 秒）后收尾；一轮唤起没有时间上限（早先是 30 分钟强杀），只在进程退出、答完收尾或用户点停止时结束；停止只对进程组发一次 `SIGTERM`（`lib/platform.ts` 的 `killTree`），不等它真退出，也没有 `SIGKILL` 兜底，紧接着就可能叫下一轮；叫醒的话整段放在一个命令行参数里，只有摘要（`SUMMARY_PROMPT_BYTES`，90 KB）和摘要句（`GIST_PROMPT_BYTES`，80 KB）按字节截断，普通叫醒和复验没有总字节上限，超了由 `spawn` 报 `E2BIG`，这一轮记成「起不来：E2BIG」。
- **关键文件**：
  - `lib/summon.ts`：`wake()`、`enqueue()`、`run()`、`launch()`、`takeQueued()`、`pauseQueue()`、`dropQueuedMessage()`、`watchStandby()`、`checkTask()`、`netRetry()`
  - `lib/lane-state.ts`：`registerLaneReader()`、`readLaneSnapshot()`、`registerLaneIdle()`、`isLaneIdle()`
  - `lib/continue.ts`：`sweepContinue()`、`ensureContinue()`、`markSeatUserStopped()`、`clearSeatUserStopped()`、`isSeatUserStopped()`
  - `lib/summary-auto.ts`：`sweepSummaryAuto()`、`ensureSummaryAuto()`、`summaryCandidates()`（摘要到期房间自己找人写，同一次到期最多叫两个人，不打断正在干活的）
  - `lib/events.ts`：流式解析各家 CLI 的 JSON / Stream-JSON 输出并判别这一轮答完了没有（`ended`，对外是 `parser.ended()`）
- **谁依赖它**：
  - 所有自动叫醒、单独回话（`whisper`）、写摘要（`requestSummary`）、上下文压缩（`requestCompact`）、持续目标（`requestGoal`）、请验收前自动复验（`requestCheck`）
  - `/api/v1/queue` 与 `scripts/bench-hook.mjs`、`scripts/bench-mcp.mjs`（中途取新消息）
  - 左栏席位队列气泡与暂停/继续/丢弃操作（`/api/v1/agents/[id]` 的 `queue_pause`、`queue_resume`、`queue_drop`）
- **以前出过什么事**：

## 2. 点名的去向（`Message.calls`）

- **是什么**：
  每一条 `@` 了席位的消息，都会在 `Message.calls` 里为每个被点名的席位建一条账单（`MessageCall`），记录它从被点名到结束的完整生命周期：
  - 进行中（`OPEN_CALL_STATES`）：`queued`（排队中）、`running`（正在跑，带 `runId`）、`retrying`（网络错误等重试中）、`held`（守候席位自己接着，暂不唤起）
  - 已了结：`answered`（已回帖，带 `replyId`）、`handed`（跑的过程中由 `/api/v1/queue` 或 MCP 桥接领走并跟当轮一块回完）、`picked`（守候中自己取走并回完）、`done`（唤起正常跑完但没单发新帖）、`stopped`（被人点停或丢弃）、`failed`（唤起报错或撞额度，带 `error`）、`cut`（服务器重启时断了）、` unwoken`（未配置自动唤起或接力满 3 轮被拦下）
- **关键文件**：
  - `lib/summon.ts`：`note()`、`wake()`、`enqueue()`、`run()`、`takeQueued()`、`stopAgent()`、`dropQueuedMessage()`、`settleOpenCalls()`
  - `lib/store.ts`：`markCalls()`、`settleCalls()`、`openCalls()`、`callsOfRun()`、`say()`、`pulse()`
  - `lib/owes.ts`：`seatOwes()`（汇总每个席位还欠着哪些 `@` 和哪些待办，驱动左栏琥珀色「欠 N 条 @」提示）
  - `lib/status.ts`：`seatState()`（由 `running`、`ranUntil`、`lastSeenAt`、`statusAt` 唯一裁定席位当前是 `working`、`idle`、`blocked` 还是 `offline`）
  - `lib/flow.ts` / `lib/flow-summary.ts`：按 `Message.calls` 绘制消息流转图
- **谁依赖它**：
  - 消息气泡底下的点名去向条（谁在排队、谁正在跑、谁回了哪条、谁失败了）
  - 左栏席位行底下的 `seatOwes`（「欠 1 条 @，已停下 N 分钟」）
  - 每次唤起提示词里的 `tasksOwedBy` 与待回消息提示
  - 流程图（Flow View）的节点连线与状态着色
- **以前出过什么事**：
  - **2026-11-12（`8be8348`）**：此前点名一条消息后，如果被点名的席位正在忙、守候、唤起失败或跑完没发新帖，气泡底下看不出这句 `@` 到底去了哪里，也分不清席位是不是还欠着回复。该提交引入 `Message.calls` 全状态机、`lib/owes.ts` 和 `lib/status.ts` 的 `seatState()`，把所有去向统一收口。
- **现在哪段测试管它**：
  - `scripts/test-room.mjs`：「Message.calls records every seat a message @-mentions and settles each to its outcome」段落（完整覆盖 `running` → `answered`、`queued` → `answered`、`queued` → `handed` → `answered`、唤起失败退出码非零 → `failed` 且 `seatOwes` 算作仍欠回复、未绑会话 → `unwoken`）。
  - `scripts/test-faults.mjs`：`call-fail-no-note`（若 `markCalls` 不记录 `failed` 去向，测试在断言 `end4?.state === "failed"` 时当场失败）。
- **哪些情况没有测试**：
  - 席位在 `held`（守候）状态下直接通过 `bench_messages` / `bench_wait` 读走消息并回复后从 `held` 转为 `picked` → `answered` 的分支；
  - 唤起撞上用量额度（`limited`）后用户在卡片上点「算了（dismiss）」或「定时重试（schedule）」时 `Message.calls.limited` 的状态流转。

## 3. 存储和搜索索引（SQLite + FTS5）

- **是什么**：
  所有项目、席位、消息、待办、队列状态（`lane_state` / `lane_queue`）与房间长期记忆（`memories`）都持久化在 `data/bench.db`（Node.js 内置 `node:sqlite`，WAL 模式，`busy_timeout = 5000`）。消息全文检索基于 SQLite FTS5 虚拟表 `messages_fts`，由触发器 `trg_messages_ai`、`trg_messages_ad`、`trg_messages_au` 自动同步，搜索时在 SQL 层过滤掉已撤回消息（`m.recalled_at IS NULL`）；撤回消息（`recallMessage`）将 `messages.text` 清空并记下 `recalled_at`，触发器随之更新 `messages_fts`，保证撤回后的原文在主表和分词索引里都不残留。
- **关键文件**：
  - `lib/db.ts`：`getDb()`、`SCHEMA_SQL`（含 FTS5 触发器）、`migrateFromJsonIfNeeded()`、`dbInsertMessage()`、`dbUpdateMessage()`、`dbQueryMessages()`、`dbSaveLane()`、`dbLoadLanes()`、`dbUpsertMemory()`
  - `lib/store.ts`：`load()`、`save()`、`say()`、`recallMessage()`、`queryMessages()`、`upsertMemory()`
  - `lib/backup.ts`、`scripts/restore-bench.mjs`：每天 `VACUUM INTO` 一致性备份、只读 `quick_check` 与非空校验、保留最近 7 份好备份、`npm run restore` 另存现库并找回
- **谁依赖它**：
  - 整个房间的全部读写接口（`/api/v1/room`、`/api/v1/messages`、`/api/v1/say`、`/api/v1/recall`、`/api/v1/tasks`、`/api/v1/memory` 等）
  - 顶栏消息搜索框与 MCP 工具 `bench_messages`（带 `query` 参数时走 FTS5 检索）
- **以前出过什么事**：

## 4. 重启后的恢复

- **是什么**：
  每次唤起子进程启动时，先把这轮唤起记进 SQLite 的 `runs` / `run_steps` 表（`lib/runs.ts`；早先是 `data/runs.json`。`status: "running"`，含当时在回的 `body`、`replyTo`、`ask`、`project`），并把席位队列同步到 SQLite 的 `lane_state` / `lane_queue`。服务器重启后第一次请求进入 `boot()` → `ensureSummon()` 时：
  1. `lib/runs.ts` 的 `state()` 把重启前仍标着 `running` 的记录全部改成 `status: "failed", interrupted: true`，放入 `unannounced`；
  2. `lib/summon.ts` 的 `lanesMap()` 从 `dbLoadLanes()` 恢复各席位队列，凡是有积压工作（`hasWork`：`pending`、`carry`、`summary`、`compact`、`goal`、`whisper` 任一非空）的席位**一律自动设为 `paused = true`**，防止重启瞬间风暴式并发拉起一堆子进程或插队到被打断的那轮前面；
  3. `settleOpenCalls()` 扫描所有项目的未结 `Message.calls`：还在恢复出来的队列里（`pending` 或 `carryIds`）的保留 `queued`（等重试的 `retrying` 改回 `queued`），其余随着旧进程消失的 `running` / 失效 `held` 全部对账记为 `cut`（「房间重启时断了」）；

  5. **房间自己接上**（2026-11-17 起，`scheduleRestartResume()` / `resumeSeatAfterRestart()`）：启动 60 秒后开始，一个席位一个席位来，每个隔 30 秒；被打断的唤起走 `rewake(runId, true)`，只是排着队被这次重启停住的队列去掉暂停再跑。**只接这次重启打断的**：`lane_state.paused` 记成 2 表示「重启停的」（`Lane.restartPaused`），1 是用户停的；只有这次启动时从 0 变成 2 的（`bootPaused`）才放开。用户停的、上次重启停了没接上的、用户点过「停止」的席位、撞了额度的客户端，都不动；用户暂停着队列、当时又有一轮在跑的，被打断的那一轮也不自动叫回（`rewake` 会顺带解开暂停），留给用户点「重新叫醒」。

  - `lib/db.ts`：`dbSaveLane()`、`dbLoadLanes()`

## 5. 入座、换脑和凭证轮换

- **是什么**：
  管理席位的身份凭证（`agent.token`）与底层 AI 会话绑定（`agentName` + `sessionUuid`）：
  1. **入座（`join`）**：校验项目名（多项目未传 `project` 返 400）；防同名不同客户端顶替（返 409）；首次拿到 `agentName + sessionUuid` 时生成 `randomBytes(18).toString("hex")` 席位 `token`；
  2. **换脑（`rebindAgent` / `rebindSession`）与切回旧绑定（`restoreAgentBinding`）**：在同一个席位上切换 AI 厂家或会话 UUID 时，把旧绑定压栈到 `previousBindings`，**立刻重新生成新的 `agent.token`**，并把席位的 `seenSeq` 钉到当前最新消息序号、置 `reboundNeedCatchup = true`（确保新大脑第一次被叫醒时收到近 20 条上文 + 置顶长期记忆 + 角色设定，且不重复回答旧大脑已回过的消息）；
  3. **拦截旧会话抢座**：在 `join()` 中检查来访的 `(agentName, sessionUuid)` 是否在 `agent.previousBindings` 里，若是则直接抛 `409 Conflict` 拒绝，且旧会话拿着旧 `token` 调 `/api/v1/say` 等接口一律在 `requireAgent()` 抛 `401 Unauthorized`；
  4. **MCP 桥接自动续期（`scripts/bench-mcp.mjs`）**：当桥接进程遇到 401 时调 `reclaimSeat()`，仅当前会话确实是席位当前绑定（非 `previousBindings`）时才拿回新 token，旧会话重连会被 409 拦死。
- **关键文件**：
  - `lib/store.ts`：`join()`、`requireAgent()`、`rebindAgent()`、`restoreAgentBinding()`、`wakePrompt()`
  - `lib/spawn.ts`：`rebindSession()`、`switchBackBinding()`、`spawnAndJoin()`、`writeSeatProfileFiles()`
  - `scripts/bench-mcp.mjs`：`callRoom()`、`reclaimSeat()`、`readSavedSeat()`
- **谁依赖它**：
  - 所有席位工具调用鉴权（`say`、`pulse`、`inbox`、`wait`、`ask`、`elevate`、`task`、`step`、`task_update`、`summary`、`memory`、`leave`）

## 6. 权限卡片、用户口令与前台跨项目守卫

- **是什么**：
  三层安全边界：
  1. **用户口令（`lib/human.ts` + `lib/http.ts`）**：所有带 `as: "human"` 的请求（发言、批权限、建待办、过验收、撤回、改设置、换脑等），在 `readBody()` 里强制校验请求头 `x-bench-human` 是否恒等匹配 `data/human-key`（64 位十六进制随机串，文件权限 `0600`，不在 HTML 或接口返回中暴露）。没有或口令不对一律返回 `403`，阻断 agent 用一行 `curl` 冒充用户批自己的权限或过自己的验收。同时 `guard()` 校验 `Content-Type: application/json` 与同源 `Origin`，阻断跨站请求。

## 7. 提问和验收

- **是什么**：
  把需要人类拍板的两件事做成硬性流程卡控：
  1. **向用户提问（`askUser` / `awaitAnswer` / `answerQuestion`）**：agent 调 `bench_ask` 在房间发出一张带选项的提问卡片，席位状态自动变为 `blocked`，`bench_ask` 阻塞等待用户点选或输入回答（最多等 30 分钟）；用户作答后（`answerQuestion`），若当时阻塞等待的 HTTP 连接还在就直接把答案带回，若连接已断开（进程已退出）则通过 `onMessage` 自动触发 `summon` 把该席位重新叫醒接着做。
  2. **待办与请验收（`createTask` / `setTaskStep` / `actOnTask` / `lib/review.ts`）**：每个待办创建时，若最后一步不是验收步骤，自动追加一步 `请 <用户名> 验收`。**严禁 agent 自己把验收这一步勾为 `done`**（`setTaskStep` 中用 `isReviewStep` 拦截并返 `403`）；**严禁 agent 在还有步骤未完成时直接调 `review` 请验收**（返 `400`）；**严禁 agent 冒充用户调 `pass` 或 `reject`**（`readBody` 的 `x-bench-human` + `actOnTask` 的 `actor.type !== "human"` 双重拦截）；移交待办（`handoff`）必须填齐 `done`、`left`、`caveats` 交接单；已完成的待办锁死不可再改（只能 `fork` 续建）。
  3. **前台代签（`lib/deputy.ts`，2026-11-17 起全房间一个开关）**：用户在前台打开「查过没问题的，自动替我收下」后，每个普通项目请验收都先复验；复验结论写入那一刻，房间按事实判断（开关开着、开关打开之后才请的验收、`signLane` 是 batch、当天不超 30 件），全过就以「前台代签」通过，不叫醒 AI。开关打开前就在等的永远留给用户。代签可由用户重开，重开会去掉旧复验。代签从不提交、推送、批权限或回答提问。
  4. **说人话（`lib/plain.ts`，2026-11-17）**：agent 建待办的标题和步骤、加步骤、请验收说明的第一行，由房间用确定的规则检查（文件名、命令、`t_` 编号、网址、带下划线或驼峰的名字、成串英文、行话词），不合格当场 400 退回并带改法；**只管 agent**，用户自己建的、`fork` 复制旧待办的、已有的待办都不查。别的测试和脚本自己建待办时标题要写大白话，否则会被退回。
- **关键文件**：
  - `lib/store.ts`：`askUser()`、`awaitAnswer()`、`answerQuestion()`、`dismissQuestion()`、`createTask()`、`setTaskStep()`、`actOnTask()`、`updateTask()`、`requestCheck()`
  - `lib/review.ts`：`reviewStepTitle()`、`isReviewStep()`、`signLane()`
  - `lib/deputy.ts`：`setAutoAccept()`、`autoAcceptChecked()`、`acceptDeputy()`、`reopenDeputy()`；`lib/store.ts` 的 `autoAcceptSince()`、`autoCheckHere()`、`deputyPass()`、`deputyReopen()`；`lib/summon.ts` 的 `checkTask` 里写入结论后那一行 `autoAcceptChecked`
  - `scripts/bench-mcp.mjs`：`bench_ask`、`bench_task`、`bench_step`、`bench_task_update`
  - `lib/plain.ts`：`plainFault()`、`plainRefusal()`；`lib/store.ts` 的 `requirePlain()`（`createTask`、`actOnTask` 的 `step` 和 `review` 三处调用）
- **谁依赖它**：
  - 聊天流里的提问卡片（`/api/v1/ask`）与待办看板上的「请验收 / 验收通过 / 打回」卡片（`/api/v1/tasks/[id]`）

## 8. 检查不会永远排队

- **是什么**：请验收后排上的检查，要么有结论，要么写明为什么没查。不能一直挂在「排着」。
  - 没请验收的不排。
  - 排了 15 分钟没开始就换人，最多换 2 次。
  - 检查人撞额度马上换人；全都被额度拦着就等最早的重置时间，再排一次。
  - 还不行就落成 error「没有空着的 AI 来检查」。
  - 结论攒一会儿，一次叫前台。
- **关键文件**：
  - `lib/summon.ts`：`requestCheck`、`pickAutoChecker(task, avoid)`、`repickCheck`、`noCheckerLeft`、`sweepChecks`、`ensureCheckSweep`、`checkTask`、`noteCheckSettled`、`tellChecksSettled`
  - `lib/review.ts`：`reviewAsked`、`checkStaleMs`
  - `lib/store.ts`：`runBatchCheck`、`actOnTask` 的 check、`earliestLimitReset`
- **谁依赖它**：前台的 `bench_check` 和整批卡片；页面上的「检查」按钮；前台代签（结论出来才收）。
- **以前出过什么事**：2026-11-18，Bench-bot 的 3 件检查排了好几个小时没动。原因有三：没请验收也排了；排在不动的席位上；检查人撞额度后就停在那里。前台还被每件结论各叫一次。
- **现在哪段测试管它**：
  - `scripts/test-check-queue.mjs`。
  - `scripts/test-faults.mjs`：`check-stale-no-repick`（去掉排久换人）、`check-limit-no-repick`（撞额度落成没跑成）、`check-verdicts-not-batched`（每件结论各叫一次前台），三条都会让 test-check-queue 当场失败。
- **哪些情况没有测试**：`BENCH_CHECK_QUIET_MAX_MS` 的最长等待（结论一直不断地来）；扫描定时器本身（测试直接调 `sweepChecks`，传入虚拟时间）。
